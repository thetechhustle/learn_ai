### 3.5 Session Habits That Keep You Safe

You've run a session. Before the training wheels come off in Chapter 4, this lesson installs the habits that let you move *fast* without moving *reckless* — because an agent with file access and command execution deserves the same respect as any powerful tool: not fear, procedure.

!!! abstract "What you will learn"
    - Run the pre-flight and post-flight checklists that bracket every session.
    - Set permission boundaries deliberately instead of clicking through them.
    - Know the handful of in-session commands that manage the session itself.
    - Recognize the three risk patterns that cause virtually all agent mishaps.

!!! success "Builder principle"
    Fast is a byproduct of safe. The builder with rollback and receipts takes bigger swings — because their misses cost nothing.

## The bracket: pre-flight and post-flight

Every session, both lanes, no exceptions:

**Pre-flight (30 seconds):**

- [ ] `pwd` — I'm in the right project, and it's under `~/builds`.
- [ ] `git status` — clean; everything valuable is committed.
- [ ] I can say the session's goal in one sentence. (Can't? Not ready — write the brief first.)

**Post-flight (60 seconds):**

- [ ] `git diff` reviewed — I've *seen* what changed, not just heard about it.
- [ ] Result tested by me, as a user, per my "done means."
- [ ] `git add . && git commit -m "..."` — or `git restore .` with zero guilt.
- [ ] `git push` — locked the door on the way out.
- [ ] One journal line: what worked, what didn't.

That's 90 seconds of ceremony buying you unlimited experimental courage. Best trade in the business.

## Permissions: gates, not speed bumps

When Claude Code asks "may I run this command / edit this file," that's a **gate**, and you're the gatekeeper. The professional move is a quick three-part read:

1. **What** is it trying to do?
2. **Where** — inside this project, or reaching outside it?
3. **Reversible?** File edits in a committed repo: yes, trivially. Deletions, installs, anything touching the network or systems outside the folder: slow down and actually read.

As trust builds, Claude Code lets you pre-approve categories of routine actions so the gates you *do* see are the meaningful ones. That's the right evolution — reduce noise, never attention. What you're building toward (Chapter 9) is codified guardrails via hooks and settings, where your policy runs automatically. For now: read the gates.

!!! warning "The three patterns behind almost every mishap"
    1. **Wrong room** — session started in the wrong directory; agent edits files you didn't mean to expose. *Killed by:* `pwd` in pre-flight.
    2. **No snapshot** — uncommitted work meets a sweeping change; no way back. *Killed by:* `git status` in pre-flight.
    3. **Rubber-stamping** — approving gates on autopilot, including the one that mattered. *Killed by:* the three-part read, plus keeping sessions short enough that attention survives.

## Managing the session itself

A few commands operate on the *conversation* rather than your files — learn these now, they appear in every future chapter:

| Command | What it does | When |
| --- | --- | --- |
| `/clear` | Wipes conversation context, fresh start | Between unrelated tasks — stale context pollutes (Lesson 2.2) |
| `/cost` | Shows what this session has spent | Whenever you're curious; weekly at minimum |
| `/help` | Lists available commands | When you forget the others |
| ++esc++ | Interrupts the agent mid-action | The moment you see it heading somewhere wrong — steer early, don't wait |
| `/exit` | Ends the session | Post-flight time |

The deeper skill behind `/clear`: **one task, one context.** When the site's done and you're switching to the newsletter draft, clear. You're managing the whiteboard now — that's Lesson 2.2 turned into muscle memory, and Chapter 5 builds a whole discipline on it.

## Secrets: the one non-negotiable

API keys, passwords, customer data — these never go in project files, never in briefs, never in anything that gets committed or pasted. If a build needs a key (Chapter 8 will), it lives in an environment variable or a `.env` file listed in `.gitignore` — the lesson that needs it will show the exact setup. A leaked key on public GitHub gets found by scanners in *minutes*. This rule has no exceptions and no "just for testing."

## Try it now

Run one complete bracketed session, end to end:

1. Full pre-flight in `quick-win`.
2. Session goal: `Add a short "Now Learning" section to my site listing three things from this course, styled to match.`
3. During: read every gate with the three-part read. Interrupt once with ++esc++ just to feel the brake, then let it continue.
4. Full post-flight, including the journal line.

Do this bracket every session for the next week and it stops being a checklist — it becomes how you work.

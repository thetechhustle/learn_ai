# 2.2 Tokens, Context Windows, and Memory

If Lesson 2.1 was the engine, this is the fuel gauge. Tokens and context windows sound like trivia until you realize they explain the most frustrating behaviors you'll ever see from an AI — forgetting things mid-conversation, quality dropping in long sessions, costs creeping up. This lesson turns them into planning tools.

!!! abstract "What you will learn"
    - Explain what a token is and roughly convert between tokens and words.
    - Describe the context window as working memory, and predict what happens when it fills.
    - Distinguish training, context, project files, and product-managed memory or retention.

!!! success "Builder principle"
    The context window is a budget. Builders who spend it deliberately get senior-level output; builders who ignore it get amnesia.

## Tokens: the model's syllables

Models don't read words — they read **tokens**, chunks of roughly ¾ of a word each. `understanding` might be two tokens (`understand` + `ing`); common short words are usually one; code and unusual text break into more.

Rules of thumb worth memorizing:

| Text | Tokens (rough) |
| --- | --- |
| One word | ~1.3 tokens |
| One page of prose | ~500 tokens |
| A typical source-code file | 500–2,000 tokens |
| A whole novel | ~120,000 tokens |

Why care? Two reasons: **cost** (API pricing is per token, in and out) and **capacity** — which brings us to the main event.

## The context window: working memory

The **context window** is the maximum input and output budget for one model interaction: instructions, conversation, retrieved material, tool results, and the answer being generated. Modern models may accept hundreds of thousands of tokens, but capacity is not perfect recall. Information can be overlooked, under-weighted, or confused even while it technically fits.

Picture a whiteboard. Everything relevant must be *on the board* while the model works. When the board fills, something has to come off — older conversation gets summarized or dropped. That's why:

- A chatbot can miss something you told it earlier — it may have been compacted, dropped, or simply under-attended among other material.
- Long agent sessions can drift in quality — the board is crowded with stale detail, diluting what matters.
- Claude Code has commands like `/clear` and automatic *compaction* (summarize-and-continue) — deliberate board management, which you'll use from Chapter 4 on.

And a subtler effect that separates pros from beginners: **it's not just about fitting — it's about focus.** A model reasons best about what's prominent and relevant in context. Stuffing the window with everything you have is like briefing a contractor by handing them your entire filing cabinet. Curation beats volume. That principle has a name — context engineering — and it's Chapter 5.

## Four things people call "memory"

People say "the AI remembers/forgets" about three different things. Untangling them dissolves most confusion:

1. **Training knowledge** (baked in) — patterns learned during training. Broad, imperfect, and bounded by the training process. You do not edit it; you choose a model.
2. **The context window** (working material) — text and tool results available for the current turn. It is finite and imperfectly attended. You shape it, but the product assembles some of it too.
3. **Project memory** (files on disk) — CLAUDE.md, memory files, and a second brain that an agent can read across sessions. You can inspect and version these files, subject to normal filesystem and team controls.
4. **Product-managed memory and retention** — account memory, saved chats, telemetry, server logs, caches, and retention policies managed by the service or organization. These are not the same as project files and are not necessarily erased when a terminal session closes. Check the current product, organization, and provider data controls before using sensitive information.

=== "🌱 No-code lane"

    The project takeaway: a fresh work session should not be assumed to carry today's project decisions unless they are in an approved persistent source it reads tomorrow. Separately, do not assume the service retained nothing; privacy and project memory are different questions.

=== "⚙️ Engineer lane"

    At the model API boundary, each generation receives an assembled input; applications may rebuild that input from conversation history, caches, retrieval, files, account memory, and tool results. Ask both questions: "what enters this turn?" and "what does the surrounding service retain?"
